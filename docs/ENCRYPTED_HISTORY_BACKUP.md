# Mandy AI — encrypted local history backup container v1

An internal history-only container, not a full character backup or user-facing release feature. Wire layout: ASCII MANDYB01 (8 bytes), signed positive big-endian int32 manifest byte length, exact existing authenticated MANDYM01 manifest, then ordered repetitions of positive big-endian int32 encrypted chunk length and exact MANDYH01 bytes, ending at EOF. No ZIP or compression. Bound: 512 MiB per file, 4096 manifest chunks, existing 4 MiB+36 chunk cap. The manifest authenticates ordering, length and SHA-256 digest of the exact ciphertext; the history key authenticates/decrypts each chunk on restore. Manifest and history keys must be separate dedicated 32-byte keys. The wrapper's magic and frame lengths are structurally validated. Snapshot replay and omitted database records are not prevented by the manifest. No key management, deletion propagation or cloud transport.

HistoryBackup.write verifies the manifest and every staged encrypted chunk before atomic replacement of an explicitly selected target; file data is synced before publication. Existing target survives ordinary pre-publication failures. No fallback to non-atomic copy; supported filesystem required. capture stages only encrypted pages in a caller-supplied existing private directory and cleans its own files in finally. Up to roughly twice the encrypted backup size may be needed for staging and publication, plus any prior target. It assumes exclusive trusted local staging/target paths and no concurrent modification; no process-death cleanup or directory fsync, no free-space reservation. A cleanup error can occur after publication. write/capture authenticate container structure and ciphertext descriptors, not decrypted content; restore performs authenticated decryption and wire validation. restore streams bounded frames and rejects truncation, extra bytes, invalid lengths and bad authentication, but must run within one transaction because late errors can follow earlier merge callbacks.

AndroidConversationStore adds internal exportBackup and importBackup methods. Export uses the existing consistent transaction for staging and packages the file after that transaction returns. Import uses one SQLite write transaction, preserving immutable conflict and clock checks. No UI, SAF, external-storage permissions, account pairing or automatic sync. Backup covers text history only, not character profiles, relationship, memory, drafts, media, models or settings. Existing local database stays plaintext. No change to schema.

Validation: exact HistoryBackup.kt and HistoryBackupSmoke.kt compiled with the existing NativeConversation, HistoryWire, EncryptedHistoryEnvelope, HistoryManifest and HistorySnapshot source on Kotlin/JVM. 31 checks passed using real local temporary files and a transaction double: multilingual restore, replay, empty backup, altered/truncated data, extra bytes, malformed lengths, wrong key/account, failed export preserving previous target, staging failure cleanup and successful capture. Android adapter source only, not SDK-compiled; no real Android SQLite execution or Windows interoperability for this new container. File-size cap not exercised at its full 512 MiB boundary. No APK/EXE, actual personal data, scheduled work or network upload. The fixture keys are never production keys.

Reproduce with kotlinc on the six production Kotlin files above (including HistoryBackup) and tests/HistoryBackupSmoke.kt, -include-runtime -d smoke.jar; java -jar smoke.jar.
