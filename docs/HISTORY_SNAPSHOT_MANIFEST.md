# Mandy AI — authenticated history snapshot manifest v1

Experimental local-only manifest for ordered encrypted text-history chunks. Wire format: ASCII MANDYM01 (8 bytes), canonical lowercase snapshot UUID (36 ASCII bytes), unsigned 32-bit big-endian chunk count, count repetitions of unsigned 32-bit big-endian ciphertext length plus 32-byte SHA-256 of the complete encrypted chunk, then HMAC-SHA256 tag (32 bytes). HMAC input is all preceding bytes followed by canonical account UUID (36 ASCII bytes). Maximum 4096 chunks, 147536-byte manifest, 4 MiB + 36 bytes per encrypted chunk. Zero chunks allowed for an empty merge. Manifest contains no plaintext message contents, but exposes snapshot ID, number and sizes of chunks, and ciphertext digests. Requires a separate independent random 32-byte authentication key, not the AES key, password, or test key. Key provisioning/rotation/secure storage not yet implemented. The manifest key authenticates the descriptor, not individual writer identity. Reference: https://csrc.nist.gov/projects/message-authentication-codes .

Python reference validates manifest HMAC before parsing descriptor rows, consumes the exact ordered sequence and rejects missing, extra, reordered or modified chunks. For local immutable staged ciphertext only, import_snapshot authenticates each AES-GCM chunk, validates history wire data and merges all chunks inside one SQLite write transaction. Late failure rolls back previous writes and logical clock. Replay of identical messages is idempotent. No network or unbounded download in a transaction; iterator must be a trusted local staged source. Large snapshots may hold the write lock for a long time; benchmark before deployment. Kotlin/JVM source implements manifest creation and verification, not multi-page Android transaction integration. Verifying the manifest does not itself decrypt or validate chunk contents. Caller must use the exact verified immutable bytes and authenticate each chunk before import; no verify-then-reopen race. No Android database schema changes. Neither implementation prevents replay of an entire older valid snapshot, proves completeness of the sender's database, propagates deletions, or authenticates a current remote head. Full export consistency, profile/memory transfer, secure pairing, cloud and rollback prevention are outstanding. Do not use with personal cloud data yet.

Validation: six Python unittest methods passed with actual SQLite and synthetic encrypted messages, including replay, empty merge, late missing/extra/reordered/modified chunk rollback, authentication, separate-key guard, and cross-page conflict/clock rollback. Kotlin compiled on JVM with existing NativeConversation and EncryptedHistoryEnvelope: 16 counted checks passed. Python created two encrypted fixture chunks and manifest; Kotlin verified and recreated the same manifest; cmp confirmed exact byte equality. No Android SDK or .NET compilation, real inference, APK, EXE, Drive upload, workflow dispatch or scheduled work. Python reference requires the optional cryptography dependency already used by encrypted_history; this suite requires it to run.

Manual tests: python -m unittest discover -s tests -p test_history_manifest.py -v. For JVM fixture interoperability, generate two synthetic encrypted v1 batches using account UUID(int=1), AES fixture bytes(range(32)), manifest fixture bytes(range(32,64)), snapshot UUID(int=99), and history_manifest.create.
