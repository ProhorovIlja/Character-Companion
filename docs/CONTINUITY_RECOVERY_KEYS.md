# Mandy AI — recovery secret and continuity key derivation v1

Internal experimental building block. No user-facing pairing, automatic backup, network, credential persistence or cloud transfer. Generate one 32-byte uniform random root secret per account using platform CSPRNG. Not a password, not a user-chosen phrase. Recovery code format is ASCII MANDY1. then canonical 36-byte lowercase account UUID, then a period and 43 unpadded base64url characters encoding the secret (87 characters total). Strict canonical decoding rejects padding, whitespace and alternate encodings. This code is a bearer secret: possession grants the ability to derive both keys. It has no independent typo checksum or authentication; a syntactically valid modified code can derive incorrect keys, detected only by authenticating existing ciphertext/manifest. Never upload, log, share on a clipboard, or use actual recovery codes in tests.

RFC 5869 HKDF-SHA256: salt is ASCII MandyAI continuity v1: followed by the canonical account UUID, IKM is the uniform random root, output length 32 bytes per purpose, with exact ASCII info strings history-aes-256-gcm and manifest-hmac-sha256. Salt is deterministic public account-specific context, not a password salt. Kotlin uses JCA HMAC-SHA256 extract and one-block expand; Python uses cryptography HKDF. Distinct domain labels separate the two purposes, matching the existing separate-key requirements. The same root/account deterministically reconstructs the keys across implementations. Different account or root yields different keys. The recovery format has no magic migration of older independently generated experimental keys. Existing envelopes and manifests are unchanged. Do not adopt real user data until secure provisioning, recovery confirmation, key lifecycle/rotation, nonce lifetime bounds, and protected storage are implemented and independently reviewed. Lost secret means derived keys cannot be reconstructed. Compromise of root exposes both derived keys; no revocation or per-device authorization yet. Kotlin close clears owned arrays only, not JCA/internal copies, immutable recovery strings or caller copies; Python immutable bytes are not securely wiped.

Validation: exact ContinuityKeys.kt and ContinuityKeysSmoke.kt compiled with existing NativeConversation, HistoryWire, EncryptedHistoryEnvelope, HistoryManifest and HistorySnapshot on Kotlin/JVM; 19 checks passed. Python cryptography independently generated fixture keys, JVM matched both exactly, reconstructed an encrypted snapshot using recovery code, rejected wrong key and checked array clearing. Five Python unittest methods passed and the new Python reference matched the JVM fixture. Synthetic fixture data only. Windows .NET implementation, Android Keystore storage, Android SDK/NDK and device validation remain pending. No native app UI, APK, EXE, user data upload, workflows or scheduled work.

Reproduction: python -m unittest discover -s tests -p test_continuity_keys.py -v (requires cryptography). Generate code.txt (no trailing newline), history.bin and manifest.bin with shared.continuity_keys.encode/derive using UUID(int=1) and bytes(range(32)) fixture secret. Run java -jar smoke.jar code.txt history.bin manifest.bin. Never generate production secrets in the test environment.
